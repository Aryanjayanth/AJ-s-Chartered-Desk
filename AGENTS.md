# AJ's Chartered Desk — System Architecture & Rules

## Architecture rules

- All business rules (allocation limits, auto-close, reversal, recurring de-dup, invoice totals) live in Postgres triggers/RPCs; the UI calls RPCs and never writes financial totals directly — why: rules must hold regardless of client.
- Role permissions are enforced via `user_roles` + RLS helper functions (`is_finance`, `is_manager`, `is_cashier`); UI role checks are cosmetic only — why: cashier/staff isolation must not depend on hidden screens.
- The three firm roles are `admin`, `staff`, `cashier`, and module access for staff/cashier is data, not code: `role_permissions` is read through `has_capability(module, action)` inside every RLS policy — why: an Admin must be able to change what a role can do without a migration.
- `has_capability` returns true unconditionally for `is_manager()`, so the Admin role cannot be restricted and a firm can never lock itself out of its own data — why: a permission matrix that can deny the owner is a support incident waiting to happen.
- A missing `role_permissions` row falls back to `permission_defaults()`, which reproduces the behaviour the app had before the matrix existed — why: a firm that never opens Roles & Permissions must not silently lose access to its own clients.
- The matrix carries an `amounts` action separate from `view`, so "can see the record" and "can see the money" are independently grantable — why: Cashiers must record payments without seeing every fee in the practice.
- `set_role_permission` forces the other four actions off when `view` is turned off, rather than storing a contradictory row — why: no point editing what cannot be opened.
- Payment records are excluded from deletion for every role, including Admin; corrections go through `reverse_payment`, and the RPC is gated on the matrix `edit` action — why: financial rows are never permanently removed.
- Expense deletion goes through the `delete_expense(id, reason)` RPC rather than a plain DELETE, because nothing references an expense row and nothing else would leave a trace — why: the only deletion in the app that is genuinely permanent has to be audited explicitly.
- `can_amounts` cannot be enforced by RLS, because RLS filters rows and cannot hide one column of a row. Lists carrying money (payments, jobs) are therefore read through `payments_list()` / `jobs_list()`, which `case when has_capability(m,'amounts') then <col> end` and so send NULL to a caller who may see the record but not the figure — why: hiding a table cell still ships the number to the browser, so a UI-only check is not a permission.
- Financial tables have no DELETE grants; corrections are cancel/reverse RPCs. Clients, Services, Jobs and Expenses do have DELETE, gated by the matrix, because their `on delete restrict` foreign keys already refuse to delete anything carrying financial history — why: the DB is the safety net for master data, while money itself stays append-only.
- Overdue status for jobs/invoices is derived at read time from due dates, not stored — why: avoids scheduled jobs.
- tsconfig relaxes noPropertyAccessFromIndexSignature/exactOptionalPropertyTypes/noUncheckedIndexedAccess/noImplicitReturns — why: keep form/record code readable.
- Multi-tenant: every business table has firm_id defaulting to current_firm_id() with a RESTRICTIVE RLS policy; super admins (platform_admins) act inside one firm via profiles.acting_firm_id — why: hard data isolation between firms without changing every query.
- Firm users join only via firm_invites consumed in handle_new_user (never signup metadata) — why: signup metadata is user-controlled.
- Avatars/logos are stored as small resized data URLs in text columns — why: public storage buckets are blocked.
- Recurring jobs are generated daily for all active firms by a pg_cron job calling generate_recurring_jobs_all (also on app open) — why: jobs must appear without anyone opening the app.
- Auto-invoicing: When a job is marked completed with auto_invoice enabled, public.auto_invoice_job RPC runs as security definer to generate the invoice and link invoice_items without exposing direct invoice creation grants to staff — why: maintains strict finance isolation while automating billing.
- Import/Export is master-data only: clients, services and client_services can be imported; jobs, invoices and payments are export-only because their statuses and totals are computed by RPCs the client cannot call — why: an import path around create_invoice/allocate_payment would void the rules above.
- One entity registry (`src/lib/io/entities.ts`) drives the import template, the file parser, row validation and the export writer, so the documented file format cannot drift from the accepted format; duplicate rows are surfaced for a per-row decision rather than auto-resolved — why: imports must be reviewable before they touch live data.
- exceljs is imported dynamically inside the import/export handlers — why: keep a ~1MB spreadsheet dependency out of the main bundle on a page only owners/admins open.
- Casting for entity-driven Supabase reads/writes is isolated in `src/lib/io/db.ts` — why: the generated types bind each table's payload shape, which cannot survive a loop over a table union.
- `npm run build` writes to `.output`, which vite's dev watcher ignores — why: watching those files alongside `npm run dev` exhausts memory (ENOMEM on Windows).
- Fees and due-day rules live on `client_services` (the assignment), never on `services`; SAC codes are gone entirely — why: service-level rates had drifted from the assignments that actually get billed, and a single column cannot represent a client spanning several financial years.
- `validate_service_required` also enforces that billing_type and frequency agree (non-recurring forces `one_time`) — why: the UI toggles between them, so the pair can contradict itself otherwise.
- The due-date preview in `src/lib/service-options.ts` deliberately mirrors `generate_recurring_jobs_for_firm`, including its rolling `ps + step - 1 day` windows rather than calendar-aligned quarters — why: a preview that disagrees with the generator would be worse than none.
